一、Spring / Spring Boot

1.1 IoC 容器与 Bean 生命周期

30秒标准答案

Spring IoC（Inversion of Control）的核心思想是控制反转——把对象的创建和依赖关系管理从代码中转移到容器。开发者只需声明依赖（@Autowired / 构造器参数），容器负责注入正确的实例。这降低了耦合度，提高了可测试性。

Bean 完整生命周期

实例化 (Instantiation)
    ↓
属性填充 (Populate Properties / 依赖注入)
    ↓
Aware 接口回调 (BeanNameAware → BeanFactoryAware → ApplicationContextAware)
    ↓
BeanPostProcessor#postProcessBeforeInitialization
    ↓
InitializingBean#afterPropertiesSet / @PostConstruct / init-method
    ↓
BeanPostProcessor#postProcessAfterInitialization  ← AOP代理在这里生成
    ↓
Bean 就绪，放入容器供使用
    ↓
DisposableBean#destroy / @PreDestroy / destroy-method

面试关键点：AOP代理（@Transactional、@Async等）是在 BeanPostProcessor 的后置处理阶段生成的。这解释了为什么自调用不经过代理——因为目标对象持有的 this 是原始对象，不是代理对象。

三级缓存解决循环依赖

// Spring 三级缓存（DefaultSingletonBeanRegistry）
/** 一级缓存：完整的 Bean 实例（已完成属性注入和初始化） */
Map<String, Object> singletonObjects = new ConcurrentHashMap<>();

/** 二级缓存：早期暴露的 Bean（已实例化但未完成属性注入） */
Map<String, Object> earlySingletonObjects = new ConcurrentHashMap<>();

/** 三级缓存：Bean 工厂（用于生成早期引用，可能是代理对象） */
Map<String, ObjectFactory<?>> singletonFactories = new HashMap<>();

循环依赖解决过程（A 依赖 B，B 依赖 A）：

  1. 创建 A：实例化 A → 将 A 的 ObjectFactory 放入三级缓存
  2. 填充 A 的属性：发现依赖 B → 去创建 B
  3. 创建 B：实例化 B → 将 B 的 ObjectFactory 放入三级缓存
  4. 填充 B 的属性：发现依赖 A → 从三级缓存获取 A 的 ObjectFactory
  5. 调用 ObjectFactory.getObject()：如果 A 需要代理则返回代理对象，否则返回原始对象
  6. 将 A 的早期引用放入二级缓存，删除三级缓存中的 A
  7. B 获得 A 的引用 → B 创建完成 → 放入一级缓存
  8. 回到 A：获得 B 的引用 → A 创建完成 → 放入一级缓存

面试追问链

Q

为什么需要三级缓存？两级不行吗？

A

如果没有 AOP，两级缓存确实够了（一级存完整 Bean，二级存早期引用）。但有 AOP 时，代理对象应该在 BeanPostProcessor 后置阶段创建——这是 Spring 的设计原则。三级缓存存的是 ObjectFactory（工厂），只在其他 Bean 因循环依赖真正需要早期引用时才调用工厂方法决定返回原始对象还是代理对象。如果去掉三级缓存在二级直接存早期引用，就必须在实例化后立即为所有 Bean 创建代理——这破坏了 Spring 的生命周期设计（代理创建应该延迟到 postProcessAfterInitialization 阶段）。三级缓存的 ObjectFactory 实现了『按需创建、延迟到最晚时刻』的设计目标。

Q

构造器注入能解决循环依赖吗？为什么 Spring 推荐构造器注入？

A

构造器注入无法解决循环依赖——因为 A 的构造器需要 B，B 的构造器需要 A，两个都无法完成实例化（连放入三级缓存的机会都没有）。Spring 会直接抛 BeanCurrentlyInCreationException。

但 Spring 仍然推荐构造器注入，原因：
1. 不可变性：依赖声明为 final，创建后不可修改
2. 强制依赖完整：构造时就保证所有必须的依赖都已注入，不会出现 NPE
3. 暴露设计问题：如果构造器参数过多，说明类的职责太重，需要拆分
4. 循环依赖是设计缺陷：用 @Lazy 或重构来解决，而不是纵容循环依赖

Q

@Lazy 是怎么打破循环依赖的？

A

@Lazy 注入的不是真正的 Bean，而是一个代理对象。构造器参数是代理，所以构造可以正常完成。只有在第一次调用代理方法时，才会从容器中获取真正的 Bean（此时对方已经创建好了）。本质上是把"创建时依赖"变成了"使用时依赖"。

Q

Spring Boot 3.x 对循环依赖的态度有什么变化？

A

Spring Boot 2.6+ 默认禁止循环依赖（spring.main.allow-circular-references=false）。官方认为循环依赖是设计缺陷，应该通过重构解决。如果确实需要，可以手动开启配置或用 @Lazy 打破。我们信贷系统升级 Boot 3.x 时就遇到了这个问题——有两个 Service 互相依赖，最终重构为引入一个中间的 Mediator 类来解耦。

踩坑警告：
1. prototype 作用域的 Bean 不会被三级缓存处理，循环依赖直接报错
2. @Async 标注的 Bean 如果存在循环依赖会出问题——因为 @Async 的代理是在 BeanPostProcessor 后置阶段创建的，和循环依赖的早期暴露时机冲突
3. 面试不要说"Spring 通过提前暴露对象解决循环依赖"就完事了——要说出三级缓存的名字和各自作用

项目结合话术：「在我们信贷系统升级 Spring Boot 3.2 时，启动直接报循环依赖错误。排查发现是 CreditService 和 RiskService 互相引用。我们的方案是引入一个 CreditRiskMediator，把两者之间的交互逻辑收敛到中间层，同时用事件驱动（ApplicationEvent）替代部分直接调用，彻底消除了循环依赖。」

1.2 AOP 原理

30秒标准答案

Spring AOP 基于动态代理实现，有两种方式：目标类实现了接口时用 JDK 动态代理（基于 Proxy.newProxyInstance），没有接口时用 CGLIB（基于字节码生成子类）。Spring Boot 2.x+ 默认全部使用 CGLIB，因为它不需要接口约束更灵活。AOP 代理在 BeanPostProcessor 后置处理阶段创建，这就是为什么自调用不走代理——方法内部用 this 调用另一个方法，this 指向的是原始对象而不是代理。

JDK 动态代理 vs CGLIB

维度JDK 动态代理CGLIB
实现方式实现接口，生成代理类继承目标类，生成子类
限制目标必须实现接口不能代理 final 类/方法
性能调用稍慢（反射）调用快（方法直接调用）
创建速度快稍慢（需要生成字节码）
Spring Boot 默认2.x 之前接口类用这个2.x+ 默认全部使用

面试追问链

Q

@Transactional 自调用失效怎么解决？

A

自调用失效的根因：类内部调用方法时用的是 this（原始对象），不经过代理，所以 @Transactional 的切面逻辑不会执行。

解决方案有三种：
1. 注入自身：@Autowired private MyService self; 然后用 self.method() 调用
2. AopContext：((MyService) AopContext.currentProxy()).method()（需开启 exposeProxy=true）
3. 重构：把需要事务的方法提取到另一个 Service 中（推荐，职责清晰）

Q

Spring AOP 和 AspectJ 有什么区别？

A

Spring AOP：运行时代理，只能拦截 Spring Bean 的方法调用，性能开销在运行时。
AspectJ：编译时/加载时织入字节码，可以拦截任何类的任何连接点（包括字段访问、构造器），功能更强大但配置复杂。

实际项目中 Spring AOP 覆盖 99% 的场景。只有在需要拦截非 Spring 管理的类、或需要极致性能（省去运行时代理开销）时才用 AspectJ。

Q

多个切面的执行顺序是什么？怎么控制？

A

同一个切面内：Around → Before → 目标方法 → AfterReturning/AfterThrowing → After → Around返回

多个切面之间：用 @Order(n) 控制，值越小优先级越高（越先进入，越后离开，类似洋葱模型）。

例如 @Order(1) 的事务切面包在最外层，@Order(2) 的日志切面在里面：事务先开启 → 日志开始 → 执行 → 日志结束 → 事务提交。

项目结合话术：「我们信贷系统有三层 AOP 切面：最外层 @Order(1) 是分布式链路追踪（设置 traceId），第二层 @Order(2) 是统一异常处理和告警，第三层 @Order(3) 是业务审计日志。这个顺序保证了即使业务异常也能被正确追踪和告警。」

1.3 事务管理

30秒标准答案

Spring 事务管理的核心是 @Transactional 注解（声明式事务），底层通过 AOP 代理 + PlatformTransactionManager 实现。最重要的两个配置是传播行为（Propagation）和回滚规则（rollbackFor）。

七种传播行为（重点三个）

传播行为含义使用场景
REQUIRED（默认）有事务就加入，没有就新建大部分业务方法
REQUIRES_NEW无论如何都新建事务，挂起当前事务独立不受外部回滚影响（如操作日志）
NESTED有事务就嵌套（savepoint），没有就新建子操作失败可回滚但不影响父
SUPPORTS有事务就加入，没有就非事务执行只读查询
NOT_SUPPORTED非事务执行，挂起当前事务不需要事务的操作
MANDATORY必须在事务中，否则异常强制调用方提供事务
NEVER必须非事务，有事务则异常极少使用

@Transactional 失效的 7 种场景

  1. 方法非 public：Spring AOP 代理只拦截 public 方法
  2. 自调用：内部 this 调用不经过代理
  3. 异常被 catch 吃掉：事务看不到异常，不会回滚
  4. 抛出 checked 异常：默认只回滚 RuntimeException 和 Error，checked 异常需要配置 rollbackFor
  5. 传播行为 NOT_SUPPORTED：以非事务方式运行
  6. 多线程：新线程不在同一个事务上下文中（事务绑定在 ThreadLocal）
  7. 数据库引擎不支持：MyISAM 不支持事务

面试追问链

Q

NESTED 和 REQUIRES_NEW 有什么区别？

A

核心区别在于是否共享物理事务：

REQUIRES_NEW：创建一个全新的、完全独立的事务。父事务回滚不影响子事务（子事务已提交就提交了）。子事务回滚也不影响父事务。

NESTED：在同一个物理事务中通过 SAVEPOINT 创建嵌套事务。子事务回滚只回滚到 savepoint，不影响父事务。但父事务回滚会连带回滚子事务（因为是同一个物理事务）。

选择：如果子操作必须独立于父操作的成败（如记录操作日志），用 REQUIRES_NEW。如果子操作失败可以忽略但父操作失败应该全部回滚，用 NESTED。

Q

你们信贷系统中事务是怎么设计的？

A

我们的放款流程涉及多步操作：扣减额度、创建放款单、记录流水、发送通知。设计原则是：

1. 核心资金操作（扣额度+创建放款单）在同一个事务中，用默认 REQUIRED
2. 操作审计日志用 REQUIRES_NEW——即使放款失败回滚，审计日志必须保留
3. 发送通知放在事务提交后执行（@TransactionalEventListener(phase=AFTER_COMMIT)），避免事务回滚但通知已发出
4. rollbackFor = Exception.class——我们强制配置回滚所有异常，金融系统宁可回滚也不能数据不一致

Q

长事务有什么危害？怎么避免？

A

长事务的危害：
1. 锁持有时间长：其他事务等待超时
2. undo log 堆积：MVCC 需要保留长事务期间所有版本，undo log 不能被 purge
3. 连接池耗尽：事务不结束，数据库连接不释放
4. 主从延迟：大事务生成大量 binlog

避免方式：
- 事务中不要有 RPC 调用、MQ 发送等耗时操作
- 查询操作放到事务外面（先查后写）
- 编程式事务（TransactionTemplate）精确控制事务范围
- 大批量操作分批提交

Q

@Transactional 的 rollbackFor 默认值是什么？为什么需要改？

A

默认只回滚 RuntimeException 和 Error，不回滚 checked exception（如 IOException、SQLException）。这是因为 Spring 沿用了 EJB 的语义。

但在实际项目中这很危险——比如调用银行接口抛出 IOException，如果不回滚，额度已扣但放款没发出去，数据就不一致了。所以我们强制要求所有 @Transactional 都配置 rollbackFor = Exception.class，并通过 checkstyle 规则扫描。

踩坑警告：
1. 最常见的坑：事务方法里 try-catch 了异常但没有重新抛出 → 事务不回滚 → 数据不一致
2. @Async + @Transactional 共存：@Async 会在新线程执行，事务上下文丢失。如果需要异步+事务，应该在异步方法内部自己开事务
3. @Transactional(readOnly=true)：不只是个标记——MySQL 对只读事务有优化：不分配事务 ID（trx_id），也不生成新的 undo log 条目（因为没有写操作）。但只读事务仍然使用已有的 undo log 进行 MVCC 一致性读。长时间的报表查询应该加这个

1.4 Spring Boot 自动装配

30秒标准答案

Spring Boot 自动装配的核心流程：@SpringBootApplication 包含 @EnableAutoConfiguration → 触发 AutoConfigurationImportSelector → 扫描所有 jar 包的 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports 文件（Boot 2.x 是 spring.factories）→ 读取到所有候选配置类 → 通过 @Conditional 系列注解过滤 → 满足条件的配置类生效并注册 Bean。

自动装配流程图

@SpringBootApplication
  └── @EnableAutoConfiguration
        └── @Import(AutoConfigurationImportSelector.class)
              └── selectImports()
                    └── 读取 META-INF/spring/...AutoConfiguration.imports
                          └── 获得候选配置类列表（如 DataSourceAutoConfiguration）
                                └── @ConditionalOnClass(DataSource.class) → 条件匹配？
                                      ├── 是 → 注册配置类中定义的 Bean
                                      └── 否 → 跳过

常用 @Conditional 注解

注解条件
@ConditionalOnClassclasspath 中存在指定类
@ConditionalOnMissingBean容器中没有指定 Bean（允许用户覆盖）
@ConditionalOnProperty配置文件中有指定属性且值匹配
@ConditionalOnWebApplication是 Web 应用

面试追问链

Q

如何自定义一个 Spring Boot Starter？

A

步骤：
1. 创建 xxx-spring-boot-autoconfigure 模块：编写 @Configuration 类 + @ConfigurationProperties
2. 创建 xxx-spring-boot-starter 模块：只有 pom 依赖，引入 autoconfigure 模块
3. 在 autoconfigure 模块的 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports 中注册配置类
4. 加 @ConditionalOnClass 等条件注解控制生效时机
5. 用 @ConditionalOnMissingBean 允许用户自定义覆盖默认 Bean

Q

@ConditionalOnMissingBean 的作用是什么？为什么需要它？

A

它的作用是：只有当容器中不存在用户自定义的同类型 Bean 时，才注册自动配置的 Bean。这实现了"约定优于配置"的理念——Starter 提供默认实现，但用户可以通过自己定义 Bean 来覆盖。

例如 DataSourceAutoConfiguration 中的数据源创建用了 @ConditionalOnMissingBean(DataSource.class)，如果你自己 @Bean 了一个 DataSource，自动配置就不生效。

Q

Spring Boot 2.x 和 3.x 的自动装配有什么变化？

A

主要变化：
1. 注册文件路径变了：2.x 用 META-INF/spring.factories，3.x 用 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports（每行一个类名）
2. @AutoConfiguration 注解：3.x 新增，替代 @Configuration + @AutoConfigureAfter/Before
3. Jakarta 命名空间：javax.* → jakarta.*（影响所有 Servlet/JPA/Validation 相关代码）
4. GraalVM 原生编译支持：AOT（Ahead-Of-Time）编译，启动时间 < 100ms

项目结合话术：「我们团队封装了一个 credit-common-spring-boot-starter，里面自动配置了：统一异常处理（@ControllerAdvice）、分布式链路追踪（TraceId 透传）、接口审计日志、Dubbo 消费者降级策略。各业务服务只需引入这个 starter 依赖，不需要重复配置。实现原理就是通过 AutoConfiguration.imports 注册多个配置类，配合 @ConditionalOnProperty 控制开关。」

二、网络

2.1 TCP 三次握手与四次挥手

三次握手

Client                           Server
  │                                 │
  │──── SYN (seq=x) ──────────────→│  第一次：客户端发起连接
  │                                 │
  │←─── SYN+ACK (seq=y, ack=x+1) ─│  第二次：服务端确认并发起
  │                                 │
  │──── ACK (ack=y+1) ────────────→│  第三次：客户端确认
  │                                 │
  │         连接建立 (ESTABLISHED)    │

为什么三次，不能两次？
防止已失效的连接请求到达服务器。假设客户端发了一个 SYN 包因网络延迟很久才到达服务器，此时客户端早已超时放弃。如果只有两次握手，服务器收到这个旧 SYN 就直接建立连接，白白浪费资源。三次握手让客户端有机会用第三次 ACK 告诉服务器"我确实想连接"。

四次挥手

Client                           Server
  │                                 │
  │──── FIN (seq=u) ──────────────→│  第一次：客户端请求关闭
  │                                 │
  │←─── ACK (ack=u+1) ────────────│  第二次：服务端确认（半关闭状态）
  │                                 │  服务端可能还有数据要发...
  │←─── FIN (seq=w) ──────────────│  第三次：服务端也关闭
  │                                 │
  │──── ACK (ack=w+1) ────────────→│  第四次：客户端确认
  │                                 │
  │     TIME_WAIT (2MSL)            │
  │     然后真正关闭                  │

为什么四次，不能三次？
因为 TCP 是全双工的，关闭需要双向各自关闭。收到 FIN 只表示对方不再发数据了，但自己可能还有数据没发完（半关闭状态）。所以服务端的 ACK 和 FIN 不能合并（除非恰好没有剩余数据）。

TIME_WAIT 为什么要等 2MSL（Maximum Segment Lifetime）？
1. 确保最后一个 ACK 能到达对方（如果丢了，对方会重发 FIN，我方能重发 ACK）
2. 让本连接的所有报文在网络中消亡，避免新连接收到旧报文

面试追问链

Q

服务器出现大量 TIME_WAIT 怎么处理？

A

TIME_WAIT 出现在主动关闭方。服务器大量 TIME_WAIT 说明服务器在主动关闭连接。

解决方案：
1. net.ipv4.tcp_tw_reuse = 1：允许复用 TIME_WAIT 连接（基于时间戳判断安全性）
2. net.ipv4.tcp_tw_recycle = 1：快速回收（NAT 环境下会出问题，Linux 4.12+ 已删除）
3. 减小 tcp_fin_timeout（缩短 TIME_WAIT 时间）
4. 根本方案：使用长连接（HTTP Keep-Alive / 连接池）减少频繁建连断连

Q

大量 CLOSE_WAIT 是什么原因？

A

CLOSE_WAIT 出现在被动关闭方。收到对方 FIN 后回了 ACK，但自己没有调用 close() 发 FIN。

根本原因：程序 bug——没有正确关闭连接（如 Socket/InputStream 没有在 finally 中 close）。

排查：用 netstat -anp | grep CLOSE_WAIT 找到对应进程，检查代码中的连接释放逻辑。常见于 HttpClient 没有关闭 Response、数据库连接没归还连接池等。

Q

SYN Flood 攻击原理和防御？

A

原理：攻击者发送大量伪造源 IP 的 SYN 包，服务器为每个 SYN 分配资源（半连接队列）并回 SYN+ACK，但永远收不到第三次 ACK → 半连接队列被填满 → 正常用户无法连接。

防御：
1. SYN Cookie：不分配资源，用加密算法编码信息到 SYN+ACK 的序列号中，收到第三次 ACK 时验证并还原 → 不占内存
2. 增大半连接队列（tcp_max_syn_backlog）
3. 减小 SYN+ACK 重试次数（tcp_synack_retries）
4. 前端负载均衡/防火墙限速

Q

TCP 的半连接队列和全连接队列是什么？

A

半连接队列（SYN Queue）：存放收到 SYN 但还没完成三次握手的连接。大小由 tcp_max_syn_backlog 控制。
全连接队列（Accept Queue）：存放完成三次握手但还没被应用 accept() 取走的连接。大小由 min(backlog, somaxconn) 控制。

如果全连接队列满了，新完成握手的连接会被丢弃（或发 RST），客户端看到的是连接超时。线上排查：ss -lnt 看 Recv-Q（当前队列长度）和 Send-Q（最大长度）。

2.2 HTTP / HTTPS

HTTP 版本演进

版本关键特性解决的问题
HTTP/1.0短连接（每次请求新建TCP）—
HTTP/1.1长连接（Keep-Alive）、管道化、Host头减少TCP建连开销
HTTP/2多路复用、头部压缩(HPACK)、服务端推送、二进制帧HTTP层队头阻塞
HTTP/3QUIC协议（基于UDP）、0-RTT建连TCP层队头阻塞

HTTP/2 多路复用：一个 TCP 连接上可以并行发送多个请求/响应，用 Stream ID 区分。解决了 HTTP/1.1 管道化的队头阻塞（前一个响应慢会阻塞后面的）。但 TCP 层仍有队头阻塞——一个包丢失导致整个连接的所有 Stream 等待重传。HTTP/3 用 UDP 从根本上解决。

HTTPS 握手过程

Client                                Server
  │                                      │
  │── ClientHello (支持的加密套件列表) ──→│
  │                                      │
  │←─ ServerHello (选定套件) ────────────│
  │←─ Certificate (服务器证书) ──────────│
  │←─ ServerHelloDone ──────────────────│
  │                                      │
  │   验证证书 → 生成预主密钥(Pre-Master Secret)
  │   用服务器公钥加密预主密钥
  │                                      │
  │── ClientKeyExchange (加密的预主密钥) →│
  │── ChangeCipherSpec ────────────────→│  双方计算出相同的对称密钥
  │── Finished (加密验证) ────────────→│
  │                                      │
  │←─ ChangeCipherSpec ─────────────────│
  │←─ Finished (加密验证) ──────────────│
  │                                      │
  │       后续通信使用对称加密              │

核心思想：用非对称加密（RSA/ECDHE）安全地交换对称密钥，后续用对称加密（AES）通信（因为对称加密快得多）。

注意：上图展示的是 TLS 1.2 RSA 密钥交换流程（已不推荐）。现代部署使用 ECDHE 密钥交换：服务端发送临时 DH 参数（ServerKeyExchange），双方独立计算共享密钥，实现前向安全（即使服务器私钥泄露也无法解密历史通信）。TLS 1.3 已强制删除 RSA 密钥交换，只保留 ECDHE。

面试追问链

Q

HTTP/2 的多路复用和 HTTP/1.1 的长连接有什么区别？

A

HTTP/1.1 长连接：一个 TCP 连接可以串行复用（发完一个请求等响应，再发下一个）。虽然有管道化但因为队头阻塞实际很少使用，浏览器通常开 6 个并行 TCP 连接。

HTTP/2 多路复用：一个 TCP 连接上并行处理多个请求/响应。每个请求是一个 Stream，用帧（Frame）传输，帧上有 Stream ID 标识归属。不需要排队等待，真正的并发。

Q

如何防御中间人攻击？

A

HTTPS 通过证书链验证防御中间人：
1. 服务器证书由受信任的 CA 签发（浏览器/OS 内置根证书）
2. 客户端验证：证书是否过期、域名是否匹配、签名是否合法（用 CA 公钥验证）
3. 证书链：服务器证书 → 中间CA证书 → 根CA证书（逐级验证）

如果攻击者伪造证书，因为没有 CA 的私钥无法生成合法签名，验证会失败。
补充防御：HSTS（强制 HTTPS）、Certificate Pinning（固定证书指纹）。

Q

TLS 1.2 和 TLS 1.3 有什么区别？

A

1. 握手速度：TLS 1.2 需要 2-RTT，TLS 1.3 只需 1-RTT（且支持 0-RTT 恢复会话）
2. 安全性：TLS 1.3 删除了不安全的算法（RSA密钥交换、RC4、SHA-1、DES），只保留 AEAD 加密套件
3. 前向安全：TLS 1.3 强制使用 ECDHE 密钥交换（前向安全），即使服务器私钥泄露也无法解密历史通信
4. ServerHello 后加密：TLS 1.3 在 ServerHello 之后就开始加密，握手过程更难被窃听

2.3 TCP 粘包拆包

问题本质

TCP 是字节流协议，没有消息边界的概念。发送方发了两个"消息"，接收方可能一次收到合在一起（粘包），也可能一个消息被拆成两次收到（拆包）。

产生原因

  • 发送端：Nagle 算法合并小包（等待凑够或超时才发）
  • 接收端：应用没及时读取缓冲区，多个包堆积
  • MSS/MTU 限制：大消息被 TCP 分段

解决方案

方案实现优缺点
固定长度每条消息固定 N 字节简单；浪费空间
分隔符用特殊字符（如 \n）分割消息灵活；需要转义
长度字段 + 内容消息头放长度，后跟内容体推荐；通用高效

Netty 的解决方案

// 长度字段解码器（最常用）
pipeline.addLast(new LengthFieldBasedFrameDecoder(
    1024 * 1024,  // maxFrameLength 最大帧长度
    0,            // lengthFieldOffset 长度字段偏移
    4,            // lengthFieldLength 长度字段本身占4字节
    0,            // lengthAdjustment 长度调整值
    4             // initialBytesToStrip 跳过长度字段
));

// 分隔符解码器
pipeline.addLast(new DelimiterBasedFrameDecoder(1024, Delimiters.lineDelimiter()));

// 固定长度解码器
pipeline.addLast(new FixedLengthFrameDecoder(64));
Q

你们系统中 Dubbo RPC 是怎么处理粘包拆包的？

A

Dubbo 协议使用的是长度字段方案。Dubbo 协议头固定 16 字节，其中包含魔数（0xdabb）、请求/响应标志、序列化方式、以及消息体长度（4字节）。接收端先读 16 字节头部，解析出长度，再按长度读取完整消息体。底层基于 Netty，使用 DubboCodec（继承 ExchangeCodec）做编解码，本质上就是 LengthFieldBasedFrameDecoder 的变种。

Q

Nagle 算法是什么？什么时候需要关闭？

A

Nagle 算法：如果有已发送但未确认的数据，则将新的小数据包缓存起来，等确认到达或凑够 MSS 再发送。目的是减少小包数量，提高网络利用率。

需要关闭的场景（TCP_NODELAY=true）：实时性要求高的——如游戏、交互式终端、RPC 框架。延迟哪怕增加几毫秒都不可接受。Dubbo/gRPC 默认都关闭 Nagle。

三、系统设计

3.1 限流设计

四种限流算法对比

算法原理优点缺点
固定窗口 固定时间窗口内计数 实现简单 窗口临界点可能出现 2 倍流量
滑动窗口 窗口随时间滑动，精确计数 平滑，无临界问题 需要记录每个请求时间戳，内存开销大
漏桶 请求进入桶中，以恒定速率流出 平滑输出，绝对匀速 无法应对突发流量（桶满就拒绝）
令牌桶 以恒定速率生成令牌，请求消耗令牌 允许一定突发（桶中有积累的令牌） 实现稍复杂

面试一句话区分：漏桶控制输出速率恒定（像水龙头匀速滴水），令牌桶控制平均速率恒定但允许突发（像攒了一把游戏币可以连续用）。大部分场景选令牌桶（Guava RateLimiter 就是令牌桶实现）。

分布式限流：Redis + Lua 滑动窗口

-- 滑动窗口限流 Lua 脚本
local key = KEYS[1]                    -- 限流 key（如 rate_limit:user:123）
local limit = tonumber(ARGV[1])        -- 窗口内最大请求数
local window = tonumber(ARGV[2])       -- 窗口大小（毫秒）
local now = tonumber(ARGV[3])          -- 当前时间戳（毫秒）

-- 移除窗口外的旧请求
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)

-- 统计当前窗口内请求数
local count = redis.call('ZCARD', key)

if count < limit then
    -- 未超限：记录本次请求（score=时间戳，member=唯一值）
    redis.call('ZADD', key, now, now .. ':' .. math.random(1000000))
    redis.call('PEXPIRE', key, window)
    return 1  -- 允许通过
end

return 0  -- 限流拒绝

面试追问链

Q

令牌桶和漏桶怎么选？你们信贷系统用哪种？

A

选择标准：
- 需要严格匀速（如调用银行接口有QPS硬限制）→ 漏桶
- 需要允许短时突发（如用户请求高峰）→ 令牌桶

我们信贷系统分两层限流：
1. 网关层：Sentinel 令牌桶，限制每个用户 API 的 QPS（允许短时突发，不影响正常使用）
2. 下游银行接口：RateLimiter 漏桶/令牌桶，严格控制调用速率不超过银行给的上限（如 100QPS）

Q

Sentinel 的限流原理是什么？

A

Sentinel 用滑动窗口统计 QPS。具体实现：
1. 把 1 秒分成多个小窗口（默认 2 个，每个 500ms）
2. 用 LeapArray（环形数组）存储每个小窗口的统计数据（请求数、异常数、RT）
3. 限流判断时，把当前滑动窗口内所有小窗口的数据求和
4. 支持多种限流效果：直接拒绝、Warm Up（冷启动预热）、排队等待（漏桶效果）

Q

集群限流和单机限流有什么区别？怎么实现集群限流？

A

单机限流：每个节点独立限流，总流量 = 单机限额 × 节点数（不精确，节点间流量不均匀时会出问题）。

集群限流：所有节点共享一个计数器，精确控制总流量。

实现方式：
1. Redis 集中式：所有节点通过 Redis 做全局计数（上面的 Lua 脚本），精确但有网络开销
2. Token Server：专门的限流服务分发令牌（Sentinel 集群限流就是这个方案）
3. 本地预分配：中心节点把配额预分配给各节点，节点本地限流，定期上报和重新分配

面试追问链

Q

时钟回拨怎么办？

A

时钟回拨（NTP 校时导致时间倒退）会生成重复 ID。解决方案：

1. 等待追上：如果回拨 < 5ms，sleep 等到时间追上（简单粗暴）
2. 报错拒绝：如果回拨 > 5ms，直接报错告警，人工介入
3. Leaf-snowflake 方案：通过 ZK 定期上报时间戳，启动时对比，发现回拨则拒绝启动
4. 百度 UidGenerator：预生成 ID 到 RingBuffer，消费时不依赖实时时钟
5. 美团改良：在 ID 中加入一个原子自增的 sequence 位段，即使时间回拨 sequence 也能保证唯一

Q

为什么 UUID 不适合做 MySQL 主键？

A

两个原因：
1. B+ 树分裂：UUID 是随机的，插入时会分散在各个叶子节点，导致频繁页分裂，写性能差（相比自增ID顺序写入）
2. 空间浪费：UUID 36 字符 / 16 字节（BINARY），而 BIGINT 只有 8 字节。主键越大，二级索引越大（因为二级索引的叶子存的是主键值）

如果非要用 UUID，可以用有序 UUID（如 UUID v7 基于时间戳），或者用 BINARY(16) 存储去掉横杠的 UUID。

Q

号段模式的双 Buffer 是什么？

A

号段模式每次从DB获取一段ID（如1001-2000），用完再取下一段。问题是取号段时有一次DB查询，可能延迟。

双 Buffer 优化：维护两个号段（当前段和下一段）。当前段消耗到一定比例（如10%剩余）时，异步预加载下一段。切换时直接用预加载好的段，实现无感知切换，消除 DB 查询延迟。

美团 Leaf-segment 就是这个实现，99.9% 的情况下 ID 生成完全在内存中完成。

项目结合话术：「我们信贷系统用的是 Leaf-snowflake 方案生成分布式 ID。选它的原因：一是有序（方便按时间范围查询放款记录），二是高性能（本地生成无网络开销），三是通过 ZK 自动分配机器 ID 避免手动维护。时钟回拨问题我们通过两道防线解决：启动时校验（对比 ZK 上报的时间），运行时监测（回拨 > 5ms 直接报警并拒绝服务）。」

-- 秒杀扣减库存 Lua 脚本
local stock_key = KEYS[1]
local user_key = KEYS[2]          -- 用户已购买标记
local user_id = ARGV[1]

-- 1. 检查是否已购买（防止重复抢购）
if redis.call('SISMEMBER', user_key, user_id) == 1 then
    return -2  -- 已购买
end

-- 2. 检查库存
local stock = tonumber(redis.call('GET', stock_key))
if not stock or stock <= 0 then
    return -1  -- 库存不足
end

-- 3. 扣减库存 + 记录用户
redis.call('DECR', stock_key)
redis.call('SADD', user_key, user_id)
return 1  -- 扣减成功，后续异步下单

面试追问链

Q

如何防止超卖？

A

三道防线：
1. Redis Lua 原子扣减：GET + 判断 + DECR 在一个 Lua 脚本中原子执行，不会超卖
2. 数据库乐观锁兜底：UPDATE stock SET count = count - 1 WHERE id = ? AND count > 0，affected_rows = 0 则库存不足
3. 最终兜底：订单创建时校验库存记录，发现异常则取消订单退库存

为什么 Redis + DB 双重保障？因为 Redis 扣减后如果下游异常（MQ 丢消息），DB 层的乐观锁可以防止"Redis扣了但实际没卖出去"的少卖情况。

Q

热点 Key 怎么处理？比如一个商品库存 key 被百万请求打

A

库存分桶：把一个 stock_key 拆成 N 个子 key（如 stock:1001:0 ~ stock:1001:9），每个子 key 放 总库存/N 个库存。请求随机或 hash 到不同子 key，分散 Redis 单 key 压力。

其他方案：
1. 本地缓存 + 标记：库存不足后在本地设置标记（JVM 内 AtomicBoolean），后续请求直接拒绝不打 Redis
2. Redis Cluster：不同分桶 key 哈希到不同 slot，利用集群分散压力
3. Proxy 层合并请求：Nginx Lua 合并 100 个请求为一个批量扣减

Q

MQ 异步下单如何保证不丢单？

A

1. 生产者端：同步发送 + 确认机制（Pulsar 的 send().get() 确认持久化成功）
2. Broker端：Pulsar BookKeeper Quorum Write（3副本写2确认），保证消息不丢
3. 消费者端：手动 ACK，处理完业务逻辑（订单入库）后才确认。如果消费失败，消息重新投递
4. 兜底：Redis 库存 vs DB 订单数的对账任务，发现不一致则告警人工处理

我们的信贷系统放款流程也是类似的异步模式，通过本地消息表保证最终一致性。

Q

流量削峰还有什么方式？

A

1. MQ 异步：最常用，把同步操作变异步（上面已讲）
2. 验证码/答题：在前端增加人工操作，把瞬间流量打散到几秒内
3. 分时段放量：不是一次性开放全部库存，而是每 10 秒放 100 个
4. 排队系统：用户进入虚拟排队（基于 Redis Sorted Set），按入队时间依次处理
5. 过载保护：系统负载超阈值后直接 fast-fail 返回"系统繁忙"

踩坑警告：
1. 不要在秒杀流程中查数据库——DB 扛不住。库存用 Redis，用户是否已购用 Redis Set，订单异步入库
2. Redis 和 DB 库存不一致是必然的（异步嘛），需要对账任务兜底
3. 别忘了防刷：同一用户/IP 的请求频率限制（令牌桶），否则机器人把库存秒完

项目结合话术：「虽然信贷系统不做秒杀，但我们的放款高峰和秒杀有相似之处——大促期间授信申请量是平时的 5-10 倍。我们的流量治理思路相同：网关限流（Sentinel）→ Redis 缓存热数据（授信规则/用户画像）→ MQ 削峰（Pulsar 异步处理授信评估）→ DB 层乐观锁保证额度不超扣。核心就是'能不访问 DB 就不访问 DB，能异步就异步'。」
